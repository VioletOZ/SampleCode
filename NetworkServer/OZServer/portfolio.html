프로젝트 개요

OZServer는 다수의 클라이언트가 동시에 접속해 로비에서 방을 만들고 채팅하는 TCP 게임 룸 서버입니다. 목표는 기능 수가 아니라 "많은 동시 접속에서도 안전하고 빠르게 동작하는 서버 구조"를 만들고 숫자로 증명하는 것이었습니다. 그래서 컨텐츠(아이템, 전투)는 의도적으로 넣지 않고 공통 기반에 집중했으며, 룸 서버의 핵심 흐름을 보여 주는 최소 방 게임만 넣었습니다.

구현 기능
  • 로그인(ID만, 없으면 자동 생성) · 로그아웃 · 중복 접속 거부
  • 로그인 대기열(동시 처리 상한 + 순번 알림)
  • 로비 채널(정원 100) · 채널 이동 · 채널 채팅
  • 방 생성 / 참가 / 퇴장 / 목록(페이지) / 인원 목록 / 방 채팅
  • 방 게임: 준비 → 카운트다운 → 진행 → 결과, 서버 권한 이동 검증, 10Hz 델타 스냅샷
  • 접속자 요약, 연결 유지(하트비트), 단계적 종료
기술 스택
  • C++20, MSVC v143, Visual Studio 2022 (x64)
  • Boost.Asio 1.86 — 비동기 I/O, strand
  • Google Protobuf 5.29 — 패킷 직렬화
  • MySQL 8.0 (X DevAPI) · Redis (redis-plus-plus)
  • vcpkg manifest · Google Test · 자체 부하 테스트 봇

아키텍처 — 스레드 모델

핵심 원칙은 "게임 상태는 한 스레드만 만진다"입니다. 소켓 처리는 I/O 스레드 풀이 나눠 맡고, 방·유저·세션 상태는 GameLoop 스레드 하나에서만 바꿉니다. 두 쪽은 큐로만 만나기 때문에 게임 로직 어디에도 락이 없고, DB·Redis 결과도 같은 방식으로 GameLoop에 돌아옵니다.

규칙내용과 이유
상태는 한 스레드방·유저·세션 상태는 GameLoop에서만 읽고 쓴다 → 락·데드락이 없고, 핸들러는 단일 스레드 코드처럼 단순하게 작성
소켓은 strand세션별 strand로 읽기·쓰기·종료를 직렬화. 다른 스레드는 post로만 요청. 비동기 완료 핸들러는 shared_from_this()로 수명 보장
DB는 큐로GameLoop는 직접 쿼리하지 않음. 작업 큐 → 워커 → 결과 큐 → 다음 틱 콜백. 같은 대상의 동시 DB 작업은 요청 측(_pending_logins)에서 차단
종료 순서신호 → 접속 차단·요청 거부 → 진행 중 작업 마무리 → 세션 종료 → GameLoop 정지(지연 쓰기 비움) → 워커 정지. 멈춘 큐에 넣는 경로가 없도록 순서 고정

MessageQueue — 락을 짧게 잡는 MPSC 큐Message/MessageQueue.h
void Push(const SessionPtr& session, RawPacket&& packet) {
    std::lock_guard<std::mutex> lock(_mutex);
    _queue.push({ session, std::move(packet) });          // 패킷은 move, 복사 없음
}
// 연결 종료도 같은 큐로 → 정리는 항상 GameLoop 스레드에서
void PushDisconnect(const SessionPtr& session) { /* lock 후 push(IncomingMessage(session)) */ }

std::queue<IncomingMessage> PopAll() {                  // GameLoop가 틱마다 1회
    std::queue<IncomingMessage> tmp;
    std::lock_guard<std::mutex> lock(_mutex);
    std::swap(tmp, _queue);                               // O(1) 교환, 처리는 락 밖에서
    return tmp;
}
I/O 스레드 여러 개가 넣고 GameLoop 하나가 꺼내는 구조라, 소비자는 swap으로 통째로 가져가 락 보유 시간을 포인터 교환 수준으로 줄였습니다. 연결 종료도 이벤트로 넣어, 방 퇴장·세션 정리가 다른 스레드와 경쟁하지 않습니다.

void Register(protobuf::PacketType type, AllowedStates allowed,
              std::function<void(SessionPtr, const ProtoMsg&)> handler, RequestLimit limit = RequestLimit::None) {
    _handlers[type] = {
        [] { return std::make_unique<ProtoMsg>(); },                       // 파싱용 빈 메시지
        [handler](SessionPtr s, const google::protobuf::Message& m) { handler(s, static_cast<const ProtoMsg&>(m)); },
        &PacketUtils::SerializeStatus<Response>,                             // 거부 응답 생성기
        allowed, limit };                                                  // 받는 상태(비트마스크) · 빈도 제한 종류
}

요청·응답 타입, 받는 세션 상태, 빈도 제한을 한 줄에 함께 등록해, 상태 위반·종료 중·빈도 초과 거부 응답을 핸들러마다 만들지 않고 공통 코드가 생성합니다. 허용 상태는 기본 거부(등록하지 않은 타입·상태는 모두 거부)라 새 패킷을 추가할 때 실수해도 열리지 않고, 핸들러는 비즈니스 로직만 담습니다. 모든 응답은 공용 StatusCode로 결과를 돌려주고 조용히 버리는 요청이 없습니다.

핵심 설계와 코드 ② 송신 · 로그인 파이프라인
묶음 송신 — 평소엔 즉시 1개, 밀릴 때만 최대 64개를 한 번에Session/Session.h
void Write() {                                          // 세션 strand에서만 실행
    const size_t count = std::min(_write_queue.size(), MAX_WRITE_BATCH);   // 64
    for (size_t i = 0; i < count; ++i) {
        _write_buffers.push_back(boost::asio::buffer(*_write_queue.front()));
        _in_flight.push_back(std::move(_write_queue.front()));          // 전송 끝까지 버퍼 유지
        _write_queue.pop_front();
    }
    boost::asio::async_write(_socket, _write_buffers,               // scatter-gather, 복사 없음
        boost::asio::bind_executor(_strand,
            [self = shared_from_this()](const boost::system::error_code& error, size_t bytes) {
                if (error) { self->HandleDisconnect(); return; }
                self->_pending_bytes -= bytes;
                self->_in_flight.clear();                           // 용량 유지 → 재할당 없음
                self->_write_buffers.clear();
                if (!self->_write_queue.empty()) self->Write();
            }));
}
처음 구조는 패킷마다 async_write를 1번씩 걸어 room 4,000명에서 채팅 왕복 p99가 9.3초까지 늘었습니다. 타이머로 모으지 않고 "전송 중에 쌓인 것만 묶는" 방식으로 바꿔 저부하 지연은 그대로 두고, 같은 조건 p99를 71ms로 줄였습니다. 방 브로드캐스트는 직렬화한 버퍼 1개를 shared_ptr로 모든 수신자가 공유하고, 미전송 1MB를 넘는 느린 클라이언트는 끊어 서버 메모리를 보호합니다.
로그인 — 캐시 우선, DB는 상한과 대기열로 보호User/UserManager.cpp
void UserManager::OnCacheResult(SessionPtr session, std::string uuid, std::optional<UserRow> cached) {
    if (session->IsDisconnected()) { _pending_logins.erase(uuid); return; }
    if (cached) {                                               // Redis 적중 → DB 없이 완료
        _pending_logins.erase(uuid);
        _write_buffer.Put(WriteKind::LoginDate, cached->id);    // login_date는 지연 쓰기로
        CompleteLogin(session, uuid, cached->id, std::move(cached->nickname), "cache");
        return;
    }
    if (_shutdown_code != protobuf::OK) { /* 종료 중: 새 DB 작업 만들지 않고 거부 */ }
    if (_inflight < _max_inflight && _waiting.Empty()) {    // 여유 있으면 바로 DB
        StartLogin(std::move(session), std::move(uuid));
        return;
    }
    if (!_waiting.TryPush({ session, uuid })) { /* 대기열 10,000 초과 → ERR_SERVER_BUSY */ }
    SendQueuePosition(session, waiting, waiting);              // 1초마다 순번 알림
}
로그인은 Redis 조회 → 미적중이면 DB(cache-aside)입니다. DB로 동시에 넘기는 로그인은 워커 수 × 8개로 제한하고 나머지는 FIFO 대기열에서 순번을 알려 줍니다(16·32·64를 측정해 64 채택). Redis가 멈춰도 1초 동안은 바로 미적중 처리해 로그인은 DB로 계속됩니다. 같은 ID의 동시 요청은 처리 중 목록으로 막아 DB 워커가 여러 개여도 같은 계정 작업이 겹치지 않습니다. SQL과 행 매핑은 DAO(Data/UserTable)에만 두어 게임 로직에는 SQL이 없습니다.

지연 쓰기 큐 — 잦은 쓰기를 모아 묶음 1건으로Db/DbWriteBuffer.h · Data/DbWriteKinds.cpp
void Put(WriteKind kind, int64_t key, int64_t value = 0) {     // GameLoop 전용, 락 없음
    Buffer& buffer = _buffers[static_cast<size_t>(kind)];
    if (buffer.entries.empty()) buffer.deadline = Clock::now() + _specs[kind].interval;   // 1초
    buffer.entries.insert_or_assign(key, value);                  // 같은 키는 마지막 값만
    if (buffer.entries.size() >= _specs[kind].max_items) Flush(kind);                    // 1,000개
}
void Flush(WriteKind kind) {                                      // 버퍼를 move해서 작업 1건으로
    _queue.Push({ [write = spec.write, entries = std::exchange(buffer.entries, {})](mysqlx::Session& s) {
        try { write(s, entries); }                                // UPDATE user SET login_date=NOW() WHERE id IN (...)
        catch (const std::exception& e) { LogError(...); }
    } });
}
// 종류 추가 = WriteKind 값 + 표에 한 줄: { "login_date", 1s, 1000, 쓰기 함수(UserTable) }
로그인마다 나가던 UPDATE 6,000건이 6건이 됐습니다. 묶음은 전용 워커 1개가 넣은 순서대로 실행해 예전 값이 새 값을 덮어쓰지 않고, 정상 종료 시 모두 비웁니다. 비정상 종료 시 최대 1초분이 유실될 수 있어 재화·아이템처럼 유실되면 안 되는 데이터는 넣지 않는다는 규칙과 즉시 쓰기(WriteNow)를 함께 두었습니다.
단계적 종료ShutdownPolicy.h · GameLoop.h
bool ShouldFinishShutdown(duration elapsed,
                          bool has_pending_work) {
    if (elapsed >= SHUTDOWN_MAX_WAIT) return true; // 60s
    return elapsed >= SHUTDOWN_GRACE               // 10s
        && !has_pending_work;
}
void UpdateShutdown() {          // 종료 중 매 틱
    _db_write_buffer.FlushAll();
    if (ShouldFinishShutdown(elapsed,
            _user_manager.HasPendingLogins()))
        _on_shutdown_ready();    // 세션 종료 시작
}

bool Update(Clock::time_point now) {       // 준비·퇴장은 값만 바꾸고, 전환 조건은 여기서만 확인
    switch (_phase) {
    case GAME_WAITING:   if (everyone_ready) next = GAME_COUNTDOWN; break;        // 2명 이상 전원 준비
    case GAME_COUNTDOWN: if (!everyone_ready) next = GAME_WAITING;                // 준비 취소·퇴장
                         else if (time_up) next = GAME_PLAYING; break;
    case GAME_PLAYING:   if (!enough_players || time_up) next = GAME_RESULT; break;
    default:             if (time_up) next = GAME_WAITING; break;                 // 결과 5초 후
    }
    if (next != _phase) { ... }                    // 진입 처리(시작 위치, 순위 등) 1회, 이어서 코인 생성
    return std::exchange(_state_changed, false);   // true면 Room이 S_GameState를 방 전원에게
}
